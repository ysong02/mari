# SALSA node and gateway

SALSA is a swarm attestation protocol that combines standards-based authentication with lightweight attestation mechanism and integrate both into the network-join procedure.
This allows both device identity and software state verification before swarm admission.

SALSA is suitable for any dense IoT deployment requiring low-latency communication. 

## Key Features

- **Low protocol overhead:** Authentication and attestation should introduce limited communication overhead, avoiding excessive protocol traffic or delay in the swarm.

- **Scalability:** The protocol should remain efficient as the number of participating devices increases and should avoid unnecessary per-node communication when information can be shared across the swarm.

- **Resource efficiency:** The memory and energy consumption, and the processing load introduced by the protocol should remain compatible with low-power, resource-constrained embedded devices.

- **Interoperability and deployability:** The design should facilitate practical deployment and future interoperability with standards-based systems.

- **Mutual authentication:** The joining device and the network service must mutually authenticate before the device is accepted in the swarm.

- **Evidence freshness and uniqueness:** Attestation evidence must be freshly and uniquely generated for each attestation procedure and not be replayed.

- **Evidence integrity:** The verifier must be able to determine that the evaluated evidence was generated by the claimed Attester and has not been modified in transit.

- **Session binding:** Attestation evidence must be cryptographically bound to the authentication session in which it was generated, preventing evidence from one session being relayed in another.

- **Parameters agreement of authentication and attestation:** An attestation decision accepted by the Relying Party must correspond to a completed Attester session with matching security parameters.

- **Result uniqueness, freshness, and integrity:** The attestation result must be freshly generated for each request, with at most one valid result produced for the same request, and must remain unmodified in transit.

  
## Project Structure

```
repo/
├── app/                    # Example applications and tests
│   ├── 03app_gateway/     # Gateway implementation example
│   ├── 03app_node/        # Node implementation example
│   └── ...                # Various test applications
├── drv/                   # Hardware drivers
├── mari/                  # Core protocol implementation
└── nRF/                   # Nordic Semiconductor SDK files
```

## Example Usage

Gateway initialization:
```c
mari_init(MARI_GATEWAY, MARI_NET_ID_DEFAULT, schedule, event_callback);
```

Node initialization:
```c
mari_init(MARI_NODE, MARI_NET_ID_PATTERN_ANY, schedule, event_callback);
```

## Hardware Support

- nRF52833
- nRF52840
- nRF5340
